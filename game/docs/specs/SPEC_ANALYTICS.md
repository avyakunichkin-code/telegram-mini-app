# Spec: вкладка «Аналитика» (ТВОЙ ХОД)

Ближайший срез AN1 включает компактный экран «Аналитики», прогноз 3/6/12,
одну серверную рекомендацию и блок «Важные решения». В текущей игре прогноз
рассчитан на три хода, а предложение о вложении делит сумму 50/50.
Продуктовый объём согласован по итогам интервью 18–19.11.2026.
[Канон геймдизайна](../canon/GAME_DESIGN.md#аналитика-an1).

**Эпик:** [AN1](../backlog/PRODUCT_BACKLOG.md#эпик-an1--финансовая-аналитика-игрока) · **Idea (approved):** [player-financial-analytics-an1](../vision/ideas/player-financial-analytics-an1.md) · **Лексика:** [post-playtest §лексика](../vision/ideas/post-playtest-wave1-two-directions.md) · **Метрики:** [ADR-009](../decisions/ADR-009-metrics-dictionary-tb1.md).

### Определение продукта

| Вопрос | Ответ |
|--------|--------|
| Где в UI? | Вкладка **«Аналитика»** (`AnalyticsPremium`, `MqxAnalyticsPage`). |
| Продукт | GAME, профиль `save_kind=game`. Режим Plan снят по [ADR-013](../decisions/ADR-013-game-only-drop-plan-mode.md). |
| Backend | Выбирает рекомендацию и исполняет правила. Frontend отображает результат. [Канон backend](../canon/BACKEND.md#правила-рекомендаций-an1). |

## 1. Цели экрана

| Цель | Как поддерживается |
|------|--------------------|
| **Текущее состояние** | Счёт, подушка и число ходов расходов, которые она покрывает |
| **Деньги за ход** | Текущие доходы, полные расходы и разница между ними |
| **Динамика и траектория** | История счёта и подушки, текущая точка и прогноз на 3/6/12 ходов |
| **Следующее действие** | Одна применимая рекомендация по правилам backend |
| **Вспомнить партию** | Названия активных цепочек событий и последние решения игрока |


---

## 2. Принципы UX

1. **Один главный KPI на блок** — подписи единиц и смысла (см. ADR-009).  
2. **Термины = экономика месяца** — как на главной и в «Капитале».  
3. **Числовые ориентиры** — используем согласованные правила рекомендаций.
4. **Прогноз — ориентир**, не обещание: disclaimer про события и сделки.  
5. **Ранние периоды** — пустые состояния с короткой подсказкой Монетки.  
6. **Цвет как смысл** — брендбук; a11y: текстовые дубли у баров.

## 3. Структура экрана (канон AN1)

Ближайший AN1 сохраняет компактную структуру утверждённого экрана.

| Блок | Содержание |
|------|------------|
| **Счёт и подушка** | Номер хода, остаток на счёте, сумма подушки и её размер в ходах текущих расходов |
| **Рекомендация** | Одна применимая рекомендация с наивысшим приоритетом |
| **Деньги за ход** | Доходы, полные расходы, остаток или дефицит |
| **Счёт + подушка** | До трёх закрытых ходов, текущий снимок и прогноз на 3/6/12 ходов |
| **Важные решения** | Название активной цепочки и последнее решение игрока |

ПДН, отдельный блок устойчивости, водопад расходов и таблица шести закрытий
отложены за пределы ближайшего среза. Пороги ниже относятся к будущим расширениям.

### Важные решения

Каждая строка содержит название активной цепочки и последнее решение игрока по
ней. Состояние цепочки используется для отбора строк. На экране достаточно этих
двух полей. Активными считаются цепочки, которые ждут продолжения или уже показали
очередное событие. Данные берём из текущей партии. Если список пуст, блок скрывается.
Источник состояния — [серверный жизненный цикл цепочки](../../api/app/events/chains.py).
Связь с историей выбора и формат ответа определяются при проектировании API.

### 3.1. Стандарты порогов (config)

Для отложенного блока устойчивости рассматривался `analytics_thresholds` в конфигурации GAME.

| Ключ | Дефолт (ориентир) | Использование |
|------|-------------------|---------------|
| `cushion_months_comfort` | 6 | Зелёная зона подушки |
| `cushion_months_min` | 3 | Жёлтая ниже — внимание |
| `dti_attention_pct` | 40 | ПДН / `liabilities_to_income_ratio` |
| `dti_critical_pct` | 50 | Критичная зона |
| `burn_income_attention_pct` | 50 | Lifestyle / доход |
| `runway_critical_months` | 1 | Runway по обязательствам |

Банковский контекст ПДН и нормы ликвидности — для **копирайта** и rule engine, не для изменения игрового баланса шаблонов.

### 3.2. Метрики снимка (ADR-009)

| Показатель | Поля / формула |
|------------|----------------|
| Ликвидность | `cash_balance + safety_fund_balance` |
| Structural net | `net_monthly_cashflow` |
| Lifestyle burn | `monthly_burn_total` / `getMonthlyBurn` |
| Full outflow | `structural_obligations + lifestyle_burn` (= `total_monthly_outflow` когда в overview) |
| **Остаток месяца** | `total_income_steady − full_outflow` (явный KPI в UI) |
| Подушка в месяцах | `safety / pressure_monthly` (из victory snap / overview) |
| ПДН | `liabilities_to_income_ratio` |

**Правило UI:** если текст про «хватит ли на жизнь» — показывать **остаток после full outflow**, не только structural net.

### 3.3. Прогноз 3 / 6 / 12 месяцев

- **UI:** `MqxSegmentedControl` — 3 | 6 | 12.  
- **Модель v1:** `liquidity_now + months × monthly_delta`, где `monthly_delta` = текущие доходы минус текущие полные расходы (`total_monthly_income − total_monthly_outflow`).
- **Не моделируем:** события, новые кредиты/покупки.  
- **Copy:** «Если ближайшие месяцы похожи на текущую финансовую модель».

Переключатель 3/6/12 подключён в игровой вкладке по утверждённой компоновке.

### 3.4. Одна приоритетная рекомендация

[Утверждено 18.11.2026](../canon/GAME_DESIGN.md#аналитика-an1): показываем одну
применимую рекомендацию с наивысшим приоритетом:

1. Просрочка.
2. Нехватка на ближайшее списание.
3. Текущие полные расходы выше доходов.
4. Перераспределение избытка подушки по §3.7.
5. Базовое распределение свободных средств по §3.6 с самостоятельным выбором инструмента.

Доходности и способ начисления показываем по §3.5.
[Утверждено 19.11.2026](../canon/GAME_DESIGN.md#отсутствие-применимой-рекомендации):
если ни одно условие не выполнено, блок рекомендации скрывается. При нулевом
остатке базовое распределение не предлагается; остальные правила проверяются.
Отрицательный остаток после списания относится к правилу нехватки на списание.
Технические границы проверок уточняются при проектировании API.

Серверный rule engine утверждён единым источником правил и выбора рекомендации.
`GET /api/finance/analytics/insights` — предложенный endpoint. Контракт, пороги,
дополнительные правила ПДН, тренда и runway требуют
отдельного согласования. Текущий экран рассчитывает рекомендацию на frontend.

Граница внешнего советника — [ADVISOR_FUNNEL_AUDIENCE](../handbook/ADVISOR_FUNNEL_AUDIENCE.md).

### 3.5. Доходность вложений

[Решение экономики](../canon/GAME_DESIGN.md#инвестиции), утверждено 18.11.2026:
новый депозит — 15% годовых с капитализацией каждый ход, облигации — 16%
с купоном на счёт каждый ход. Открытые позиции сохраняют ставку открытия.
При показе их доходности используются условия конкретной позиции.

В аналитике игрок выбирает инструмент самостоятельно. Сравнение накопленного
дохода должно учитывать капитализацию депозита и купоны облигаций, оставленные
на счёте без реинвестирования. Для 100 000 ₽ за 12 ходов это примерно 16 075 ₽
и 16 000 ₽. Новые операции и реинвестирование меняют результат.



### 3.6. Базовое распределение свободных средств

[Утверждённое правило](../canon/GAME_DESIGN.md#базовое-распределение-свободных-средств).
Применяется после проверки просрочки, нехватки на списание, дефицита за ход
и избытка подушки.

- Сначала проверяем `cash_balance − estimated_charges_total < 0` для рекомендации
  о нехватке на списание. Сумма списания берётся из `period_close_preview`.
- `free_cash = max(0, cash_balance − estimated_charges_total)`. Базовое распределение
  применяется только при `free_cash > 0`. Используются только деньги на счёте.
- Базовая рекомендация распределяет остаток строго по третям: ⅓ в подушку,
  ⅓ в выбранный инвестиционный инструмент, ⅓ оставить на счёте для событий.
- Размер подушки не меняет пропорции. Взнос в неё не ограничивается недостающей
  до ориентира суммой, переход на половины внутри базовой рекомендации отсутствует.
- Показываем одну рекомендацию, суммы и назначение частей. Игрок выбирает вклад
  или облигации и самостоятельно выполняет операции.

При проектировании API определить округление и поведение при недоступном превью списания.



### 3.7. Перераспределение избытка подушки

[Утверждено 19.11.2026](../canon/GAME_DESIGN.md#избыток-подушки):
`cushion_surplus = max(0, safety_fund_balance − 3 × total_monthly_outflow)`.
При `cushion_surplus > 0` и отсутствии более срочных условий предлагаем
перераспределить избыток в доходные позиции. Инструмент выбирает игрок.
Эта рекомендация заменяет базовое распределение по третям. Предлагаем вложить
весь `cushion_surplus`, оставив в подушке `3 × total_monthly_outflow`.
Решение утверждено пользователем 19.11.2026. Операции выполняет игрок.

## 4. Контент по фазам реализации

### Фаза A — AN1-0 (без E1)

**API:** `GET /api/finance/overview`, `GET /api/finance/analytics/timeseries?limit=48`.

- Компактный экран из §3 и прогноз 3/6/12.
- Одна серверная рекомендация по §3.4–3.7.
- Блок «Важные решения» по активным цепочкам текущей партии.

### Фаза B — AN1-1

- Отложенные возможности: таблица шести закрытий, детализация структуры расходов, ПДН и отдельный блок устойчивости.

### Фаза C — AN1-2

- Сценарий устойчивости «доход снизился вдвое» — кандидат для отложенной задачи AN1-200.
- Расширение каталога правил; breakdown по категориям при **E1**.

### Фаза D — опционально

- Личная статистика за N партий (без лидербордов).  
- **Не** сравнение с «идеальной победой» на этом экране.
