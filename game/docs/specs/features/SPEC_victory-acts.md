# Spec: победа в два акта (PR-18, вариант C)

**Статус:** DRAFT — не канон до «APPROVED» от PO. Решение PO 2026-11-01: «C как цель, временно A». Временная калибровка A уже в `SPEC_victory-v2` (пороги дохода по шаблону, финал снят).

## Assumptions

1. **Акт 1 = нынешняя цепочка после калибровки A** (обучение → подушка → доход с инвестиций по порогу шаблона). Её уже проходят к P12–18 (`chain_runner`, seed 42), отдельно перекалибровывать не нужно.
2. **Партия после победы продолжается** — это уже так ([SPEC_game-run-finale](SPEC_game-run-finale.md): `run_outcome=victory`, «Играть дальше»). Акт 2 начинается после dismiss финала акта 1, без новой партии и без нового сохранения.
3. **Акт 2 — одна-две «взрослые» цели на горизонт P25–40**, а не повтор обучения. Кандидат по умолчанию — финансовая независимость: пассивный доход покрывает долю расходов на жизнь (см. Open questions).
4. **Поражение после акта 1 остаётся поражением партии** (`cash_negative_streak` / `needs_depletion`), но в метриках видно, что акт 1 был пройден.
5. Без нового `save_kind`, без таймеров, без pay-to-win (инварианты [PLAN_production-ready](../../plans/PLAN_production-ready.md) «Не ломать»).

→ Поправь до реализации.

## Objective

**Проблема.** Цепочка победы проходится к P4–5, дальше у игрока, который всё делает правильно, 35+ ходов нет ни одного нового шага цели («нет середины игры»), а финал за 40 ходов недостижим (INV-1 на всех 4 шаблонах — [`INV-1_2026-11-01.md`](../../balance/INV-1_2026-11-01.md)).

**Что строим.** Победа в два акта: **акт 1** — первая заслуженная победа к ходам 12–18 (финал + «Играть дальше»); **акт 2** — долгая цель для тех, кто остался, с собственным финалом к ходам 25–40.

**Успех (проверяемо):**

| Критерий | Как мерить |
|---|---|
| Акт 1: `chain_runner` побеждает в окне P12–P18 на всех 4 шаблонах | `balance_playtest`, новый инвариант INV-4 |
| Акт 2: хотя бы одна политика завершает акт 2 в окне P25–P40 на каждом шаблоне | `balance_playtest`, INV-1 переопределён на акт 2 |
| Между P5 и финалом акта 1 есть хотя бы один шаг цели (нет «пустых» 10+ ходов) | `goals_met` по ряду в отчёте |
| Волна 10–20: медиана хода победы в акте 1 — 12–18; доля «цель мелковата» (Q5) ≤ 30% (гипотеза H3) | Watchtower `run_outcome` + опрос |

## Scope

### In scope

- Формат `victory_config_json` с актами (обратно совместим: без `acts` — один акт, как сейчас).
- Движок: текущий акт, цели текущего акта, `act_completed` по каждому акту.
- Overview / bootstrap: номер акта и цели текущего акта; финал (`run_finale`) после каждого акта.
- Сиды: акт 1 = цепочка A; акт 2 — по решению Open question 1.
- Баланс: инварианты INV-1 (акт 2) и INV-4 (акт 1), обновление эталонов.
- UI целей и финала: подпись «Акт 1 из 2», копирайт финала акта 1 с переходом в акт 2 — **через design-lab** (новый визуальный паттерн).

### Out of scope

- Новые механики под акт 2 (ипотека↔объект для «сдаваемой квартиры» — только если выберем этот финал; тогда отдельная задача DL1).
- Сезоны, лидерборды, советник (PR-33/34).
- Переписывание обучения внутри акта 1.

## User flows

1. **Акт 1.** Игрок проходит цепочку → на ходу 12–18 выполняет последний шаг → финал «Акт 1 пройден» (заслуги партии, отзыв) → **«Играть дальше»** / «К сохранениям».
2. **Переход.** После «Играть дальше» блок «Цель» показывает «Акт 2 из 2» и первую цель акта 2; Монетка коротко объясняет новую цель (одна реплика, не новый онбординг).
3. **Акт 2.** Обычные ходы; при выполнении цели акта 2 — финал «Партия пройдена» (второй финал), партия остаётся активной (как сейчас после победы).
4. **Поражение в акте 2.** Обычный экран поражения; в заслугах партии отмечено «Акт 1 пройден на ходу N».

## Data & API

### Models / DB

- `victory_config_json`: новое поле `acts` — массив `{ "key": "act_1", "title": "…", "goals": [...], "required_goals_met": N }`. При наличии `acts` поле `goals` верхнего уровня не используется. Без `acts` — нынешнее поведение (один акт).
- `victory_goals` (таблица): колонка `act_key` (TEXT, NULL = один акт) — миграция `00NN_victory_goals_act_key.sql` (`ADD COLUMN IF NOT EXISTS`), синхронизация в `seeds/victory_goals.py`.
- `game_profiles`: `victory_act1_at_period` (INT NULL) — ход завершения акта 1 для метрик; `run_outcome=victory` ставится по акту 1 (как сейчас при первой победе), завершение акта 2 — `victory_final_at_period` (INT NULL). Альтернатива без новых колонок — `NotificationLog` (`game_won` с `act`); решить в плане (Open question 3).

### Endpoints

Новых нет. Изменения контракта (аддитивные):

| Где | Поле | Смысл |
|---|---|---|
| `GET /api/finance/overview` → `victory` | `act_index`, `acts_total`, `act_title` | текущий акт |
| то же | `acts_completed: [{key, period_index}]` | пройденные акты |
| `win_reached` | без изменения смысла для акта 1 | обратная совместимость FE |
| `GET /api/game/bootstrap` → `run_finale` | `kind: victory_act` + `act_index` | какой финал показать |

`game/web/src/api/finance.js`, `game.js` — только чтение новых полей; старый FE без них продолжает работать (один акт).

## UI / UX

- Блок «Цель» (`MqxGoalDash`): подпись акта, точки шагов только текущего акта. **Новый паттерн → design-lab раунд** (`game/design-lab/dashboard/…acts-round/`), ★ до prod.
- Финал акта 1: тот же `run_finale` с другим заголовком и строкой «Дальше — акт 2: …». Финал акта 2 — нынешний победный.
- Копирайт: «ход», не «месяц» (PR-11).

## Rules & edge cases

- Цели акта 2 считаются **только после завершения акта 1** (как chain: следующий акт недоступен, `raw_met` может быть true).
- Если на момент завершения акта 1 цель акта 2 уже выполнена — акт 2 завершается не раньше следующего закрытия хода (не два финала подряд в одном ходе).
- `mechanics_unlock` (ADR-004) — по-прежнему от шагов акта 1; акт 2 механик не открывает.
- Старые партии (без `acts` в момент старта): конфиг читается из шаблона на лету — после выкладки они получают акты; уже победившие в старой цепочке считаются прошедшими акт 1.
- Legacy `parallel`-конфиги — без актов.

## Testing strategy

### Critical scenarios (min gate)

| ID | Сценарий | Уровень |
|---|---|---|
| CS-1 | Конфиг без `acts` → поведение и ответ overview как сейчас | unit `victory/engine` |
| CS-2 | Акт 1 выполнен → `act_index=2`, `win_reached=true`, финал `victory_act` act 1 | unit + integration bootstrap |
| CS-3 | Цель акта 2 выполнена раньше акта 1 → не засчитана до завершения акта 1 | unit |
| CS-4 | Акт 1 и цель акта 2 в одном ходе → второй финал не раньше следующего хода | integration close |
| CS-5 | Поражение в акте 2 → `run_outcome` фиксирует акт 1, экран поражения | integration |
| CS-6 | Синхронизация `victory_goals` с `act_key` (PostgreSQL) и fallback на JSON (SQLite) | unit seeds |
| CS-7 | `balance_playtest`: INV-4 (акт 1 в P12–18) и INV-1 (акт 2 в P25–40) | balance |
| CS-8 | e2e: «Играть дальше» после финала акта 1 показывает «Акт 2 из 2» | Playwright (mobile + desktop) |

```bash
# backend
cd backend && py -3 -m pytest -q
cd backend && py -3 scripts/balance_playtest.py --invariants fail
# frontend
cd frontend-react && npm run test:unit && npm run build && npm run check:guardrails && npm run test:e2e
```

## Boundaries

- **Always:** обратная совместимость конфига без `acts`; `balance_playtest` до и после; эталоны — только с согласия PO.
- **Ask first:** выбор цели акта 2; новые колонки в `game_profiles`; изменение `run_outcome`.
- **Never:** таймеры, daily-давление, платные ускорения акта; второй `save_kind`; условия победы в роутерах.

## Open questions

1. **Цель акта 2 (PO).** Варианты:
   - **(а) Финансовая независимость:** пассивный доход ≥ X% расходов на жизнь (X ≈ 50–100%). Учит главной идее игры; один X на все шаблоны, но разброс по шаблонам большой (руководитель уже на 66% к P12 — для него X нужен выше или «+N п. п. от старта»).
   - **(б) Наличные / капитал ≥ N:** прост, но учит «копить кэш», а не доход.
   - **(в) Сдаваемая квартира:** образно, но эксплойтится, пока нет связи ипотека↔объект (DL1).
   - Рекомендация: **(а)**, порог — от уровня шаблона на старте акта 2.
2. **Сколько актов:** 2 (этот spec) или 3 (обучение / стабильность / независимость)?
3. **Где хранить ход завершения актов:** колонки `game_profiles` или `NotificationLog`.
4. **Пересматривать ли пороги акта 1** после волны 10–20 (по живым данным, не по боту).
