# MQX — процесс дизайна и внедрения

Точка входа для нового дизайна Главной — [утверждение от 15.11.2026](../../../../design-lab/dashboard/APPROVED.md). Утверждённый lab определяет вид для внедрения, манифесты prod parity проверяют фактический экран.

**Концепт-картинка → обязательное MQX-превью в Design Lab → утверждение превью → подключение к игре.**

| Этап | Результат |
|---|---|
| Концепт | Покажи картинку всей страницы. Зафиксируй выбранное изображение, ширину, состояние, данные, шрифты и отдельные ассеты. |
| Design Lab | Для утверждённой картинки собери одно рабочее MQX-превью. Варианты в Lab нужны только если дизайн картинки ещё не утверждён и требуется выбор. MQX не требует нескольких вариантов. |
| Сверка | Открой превью в браузере и сравни его с картинкой при той же ширине. Проверь также 320 px и значимые состояния. Покажи расхождения и получи явное утверждение превью. |
| Игра | Подключи те же компоненты, стили и ассеты к игровым данным и действиям. Сравни скриншоты Lab и игры при одинаковых данных, ширине, теме и состоянии. Проверь сценарий в приложении. |

Превью доступно из Design Lab через маршрут каталога MQX в Vite. Используй игровую оболочку и детерминированные данные. При сравнении дождись загрузки шрифтов и изображений. Исходники CSS и ассетов веди в design, экспорты обновляй генераторами. До утверждения превью компонент доступен только в Lab и каталоге. Для опечаток и исправлений доступности без изменения компоновки отдельный раунд не нужен.

Для игрового меню и общих иконок нижней навигации сверяйся с [утверждённым каноном](../../../../design-lab/finance-game-round/MENU_APPROVED.md).

### Проверка перед показом

Перед тем как показать дизайн или превью на согласование, сам открой результат и осмотри его целиком. Рабочий экран открой в браузере, дождись загрузки шрифтов и ассетов и проверь основные действия. Сопоставь скриншот с выбранной картинкой при одинаковой ширине и состоянии. Проверь композицию, размеры, отступы, типографику, цвета, иллюстрации и кадрирование. Исправь ошибки и заметные расхождения, затем открой обновлённую версию и проверь её снова. Показывай результат, когда он близок к выбранной картинке, и обозначь оставшиеся согласованные отклонения. Если открыть результат не удалось, сообщи конкретный блокер и статус проверки.

### Эксперименты

Картинки, альтернативные компоновки и интерактивные MQX-пробы можно свободно делать и менять в Design Lab до утверждения. Рабочий процесс уточняем по результатам экспериментов. Для пробы достаточно объёма, который позволяет сравнить решения в браузере. Если выбранную картинку нужно проверить в динамике, можно собрать пробу до её утверждения. После выбора картинки достаточно одного превью для сверки и утверждения. Фиксируй канон при подключении утверждённого экрана к игре.

### Статичные раунды

Существующие HTML/CSS-раунды остаются доступны через хаб.

Запуск локально:

```bash
cd design-lab
npx serve .
# → корневой index.html — навигатор по всем витринам и prod parity
```

Или точечно:

```bash
cd design-lab/<тема>/<раунд>
npx serve .
```

Пересборка навигатора и dashboard parity: `cd frontend-react && npm run design-lab:build`

### Self-contained стили (обязательно)

`serve` отдаёт **только текущую папку** — пути `../styles.css` в HTML дают **404**.

| Файл в раунде | Роль |
|---------------|------|
| `lab-base.css` | Сборка общих стилей (`sync-lab.sh`, не править руками) |
| `styles.css` | Стили вариантов этого раунда |
| `assets/monetka-mascot.png` | Копия маскота при необходимости |

В `index.html` только `./lab-base.css`, `./styles.css`, `./assets/...`.

**Events:** `game/design-lab/events/sync-all-rounds.sh` или `./sync-lab.sh` в папке раунда.

Правило (path-scoped): `docs/engineering/CODEX-PROCESSES.md`. Скилл: `design-lab-mqx`.

## Правила утверждения

Утверждение считается полученным, когда в чате есть явная формулировка, например:

- «Утверждаем вариант **B**»
- «Берём **D**, chip ставки как в каталоге»
- «В prod — **G**, доработки только в design-lab до следующего раунда»

Явное утверждение превью открывает подключение к игровому маршруту.

## Правила внедрения (MQX)

При сборке превью:

1. Компонент(ы) — в `game/web/src/components/mqx/` (подпапки: `primitives/`, `metrics/`, `layout/`, …).
2. Стили — классы `mqx-*` в `game/web/src/styles/` (модуль по экрану, см. `styles/README.md`; barrel `index.css`), без inline hex в компонентах.
3. Экспорт — через `mqx/index.js`.
4. Секция в **`#/dev/mqx`** — обязательна до подключения к игре.
5. После утверждения превью подключи тот же MQX к игре. Делай один экран или сценарий за PR.

## Canon Sync (обязательный шаг после внедрения)

Единственный указатель утверждённых решений дизайна —
[`design-canon.json`](../../../../design/system/design-canon.json). При расхождении
статусов в документах используйте запись реестра и её ссылку на решение человека;
затем исправьте затронутые документы. Порядок для всех слоёв —
[ADR-018](../../../../docs/decisions/ADR-018-layer-decision-sources.md).

Если паттерн **утверждён** и мы его **внедрили** в `frontend-react`, то в том же PR (или сразу следующим маленьким PR) нужно обновить канон `design-lab`:

- обновить `design-lab/<theme>/APPROVED.md` (что теперь канон, что запрещено, порядок блоков),
- обновить `design-lab/<theme>/README.md` (как смотреть актуальный “prod parity”),
- при необходимости добавить/обновить **page-round** (“страница целиком”), чтобы видеть реальную композицию до новых правок.

Смысл: чтобы следующий раунд начинался не “по памяти”, а от актуального канона.

При закрытии раунда обновите рабочие ссылки и примените
[правило актуальности и архива](../../../../docs/README.md#актуальность-и-архив).
