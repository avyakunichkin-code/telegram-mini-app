# Механики по актам: развитие студента без смены сохранения

Поручение PO 2026-11-03: сначала волна; обкатываем два акта, второй — про пассивный доход. Продумать открытие авто и страховок у студента в акте 2. Это концепция, а не утверждённая спецификация или изменение экономики.

## Как устроено сейчас

`backend/app/victory/mechanics_progression.py`: доступные механики — пересечение разрешений шаблона (`template_cap`) и grants цепочки целей. У basic изначально открыты потоки и инвестиции. Для остальных шаблонов временный флаг `UNLOCK_ALL_MECHANICS_IMMEDIATELY_EXCEPT_BASIC` открывает все разрешённые разделы сразу. Актов в этом контракте нет. Одной новой подписи в UI недостаточно: разрешение шаблона продолжит блокировать раздел.

## Предлагаемая модель

- Шаблон задаёт максимум доступных механик партии; акт и цели — момент открытия. Открытие явно фиксируется и не отзывается при ухудшении финансового положения.
- Студент, акт 1: счёт, подушка, расходы, инвестиции в текущем объёме. Не меняем готовящуюся волну ради проверки новой гипотезы.
- Студент, переход в акт 2: короткое объяснение новых возможностей, затем страховки и имущество. Авто — отдельная категория имущества, а не разрешение всего каталога без разбора.
- Открыть покупку авто — не выдать бесплатный автомобиль и не обязать купить его для победы. Авто даёт новые расходы и риск, а не автоматически пассивный доход. Страховка — инструмент управления риском, также не источник дохода.
- Закрытые возможности видны с объяснением «Откроется во втором акте» (BG-2), но не отвлекают от текущей цели. Это ещё требует lab.

## Варианты для проверки после волны

| Вариант | Что открывается | Цена |
|---|---|---|
| A — всё на границе акта | Авто и страховки после первого финала | Простой переход, но сразу несколько новых решений |
| B — два шага внутри акта 2 | Сначала страховки и объяснение риска, затем авто | Ниже нагрузка; нужно обосновать условие второго открытия |
| C — по ситуации | Возможность авто по акту, подходящие страховки при появлении риска/имущества | Понятный контекст, сложнее правила доступности и событий |

Рекомендация для первого прототипа — A с необязательными действиями и короткими пояснениями. B/C рассматривать, если плейтест покажет перегрузку. Это предложение, не решение PO.

## Что определить до spec и реализации

1. Порог пассивного дохода: доля расходов, абсолютная сумма или прирост к старту акта; проверить все шаблоны и отсутствие лёгкого прохождения за счёт урезания базы расходов.
2. Каталог: авто, его содержание, продажа, доступные полисы; какие виды имущества и обязательств остаются закрыты. Не открывать весь `capital_property` ради одного авто без проверки.
3. События: фильтры наличия авто/полиса и доступности механик; игрок не получает обязательное действие в закрытом разделе. Покупка не обязательна для актовой цели.
4. Старые сохранения и уже полученные активы/полисы: не отбирать, не запускать цели повторно, не засчитывать акт 2 задним числом без решения о миграции.
5. Совместимость с `mechanics_effective`, API, guidance и финалом: одно серверное правило доступности для UI и действий, а не независимые условия.
6. Баланс: 30–40 периодов, все шаблоны, сценарии без авто и с авто, со страховкой и без; осмысленное сравнение с принятой базой. Сам факт открытия не должен быть единственной причиной победы.
