# Нативный опрос первых ходов

Направление принято владельцем 04.11.2026: «Давай сделаем это, нативный опрос
будет явно более приятен пользователю, чем какой-то там переход куда-то».
После просмотра A/B владелец выбрал одно окно с несколькими вопросами на шаг
и свободным текстовым отзывом. Реализована анкета v2: девять вопросов на трёх экранах:
4 о деньгах/подушке, 3 о завершении хода, 2 о впечатлениях. Свободный отзыв
расположен на третьем экране. Выбор человека
зафиксирован в [каноне](../../../../design-lab/playtest-survey/APPROVED.md),
текущий [lab](../../../../design-lab/playtest-survey/native-round/README.md).
Статус — локальная реализация, не выложенный релиз.

## Цель и границы

Собрать девять коротких ответов внутри игры, без внешнего сервиса, выхода
из партии, запроса имени/email/Telegram и без награды за участие. Ответ
связан с авторизованным игровым аккаунтом; анонимность не обещаем.

Один ответ на каждую версию опроса для аккаунта; текущая — `first_turns_v2`. Перезапуск/смена сохранения
не создают новую анкету. Ничего не меняется в экономике, guidance и победе.
Существующий финальный `PlayerRunFeedback` сохраняет смысл и контракт:
первые впечатления не получают вымышленный outcome victory/defeat.

Вне scope: внешние формы/таблицы, аналитическая платформа, конструктор
опросов, сбор контактов, награды, редактирование отправленного ответа,
новая версия победы, напоминания через Telegram, экспорт/уведомления.
Качественный опрос не заменяет все вопросы старого протокола или KPI Q9:
число закрытий теперь берётся из серверных записей; это другой источник.

## Вопросы и данные

Все девять ответов обязательны для отправки; участие целиком добровольное.

| Ключ | Вопрос | API-значения / подписи |
|---|---|---|
| salary | Понятно, когда получать зарплату? | yes / Да; partly / Частично; no / Нет |
| safety | Понятна разница между счётом и подушкой? | yes / Да; partly / Частично; no / Нет |
| safety_transfer | Понятно, как перевести деньги в подушку и обратно? | yes / Да; partly / Частично; no / Нет |
| expense_buffer | Понятно, зачем на счёте нужен запас на расходы? | yes / Да; partly / Частично; no / Нет |
| close | Понятно, сколько спишется при завершении хода? | yes / Да; partly / Частично; no / Нет |
| close_result | Понятно, что изменилось после завершения хода? | yes / Да; partly / Частично; no / Нет |
| blocked | Было место, где не смог продолжить? | boolean; false / Нет; true / Да |
| difficulty | Как тебе сложность игры? | easy / Легко; normal / Нормально; hard / Сложно |
| continue_playing | Хочется сыграть ещё несколько ходов? | yes / Да; unsure / Не уверен; no / Нет |

Комментарий необязательный, до 1000 символов после trim, пустая строка
допустима. Подсказка: «Не указывай личные данные. Ответ увидит команда игры».
Текст выводится как текст, без HTML/Markdown. Draft только в памяти текущего
открытия. Не писать ответы в localStorage, URL, лог, Telegram или git.

## Игровой сценарий

1. Приглашение доступно после **пяти фактически закрытых ходов** текущей
   партии: count `period_economy_closings`, не `period_index >= 5`.
2. После закрытия итогов предложить «Ответить» / «Позже». Не открывать
   поверх обучения, карусели, sheet/modal или финала. Если условия мешают,
   дождаться свободного dashboard; ранний проигрыш не блокирует меню.
3. «Позже» или крестик приглашения сохраняют отказ от автоматического
   показа на эту версию. Опрос остаётся в меню «Поделиться впечатлением».
   Закрытие самого опроса также подавляет автоматический показ; черновик
   не отправляется. Повторное открытие из меню доступно до отправки.
4. Из меню можно ответить раньше пяти ходов в существующей начатой партии,
   в том числе завершённой. Без начатой партии — объяснение и disabled.
5. При отправке кнопки защищены от дубля; ошибка оставляет ответы и кнопку
   повтора. Успех показывается только после подтверждения сервера.
6. После ответа повторного приглашения нет. Меню показывает статус
   «Спасибо, ответ получен», без повторного заполнения и редактирования.

Перед отправкой клиент передаёт ID показанной партии. Если партия была
переключена в другой вкладке, ответ всё равно относится к показанной своей
партии; чужая партия никогда не доступна. UI сбрасывает draft при смене
профиля внутри текущей вкладки и не отправляет его в новую партию.

## Совместимость версий

Отправленные v1 (пять вопросов) не меняются и не дополняются вымышленными
ответами. V2 (девять вопросов) сохраняется отдельной строкой под своим ключом.
Watchtower группирует версии в разные таблицы с соответствующим набором колонок.
Ответ v1 и «Позже» v1 не считаются ответом/отказом v2.

Старый клиент без параметра survey_key в GET/bootstrap и без поля версии в
POST/dismiss продолжает работать с v1. Текущий frontend явно запрашивает v2
в GET /api/game/playtest-survey и /api/game/bootstrap и передаёт v2 при
submit/dismiss. Поля answers валидируются строго по версии: пять ключей для
v1, девять для v2; неизвестная версия/неверный набор дают 422.
Новой SQL-миграции для v2 нет: 0051 уже содержит survey_key и JSON-ответы.

## Хранение и API

Таблица `player_playtest_surveys` создаётся миграцией
`0051_player_playtest_surveys.sql`.
DDL-only baseline не переписывать. SQLite — ORM create_all только тесты.

Поля: id, user_id FK, survey_key, state (dismissed/submitted),
game_profile_id FK, template_key, period_index, closed_turns,
answers_json, comment, created_at, dismissed_at, submitted_at.
UNIQUE(user_id, survey_key). При dismiss answers отсутствуют; при submit
снимок template/period/closed_turns вычисляется сервером из своей партии,
не берётся из запроса. Версия опроса не равна версии билда: текущие отзывы
привязывать также к закреплённой версии волны в ops-листе.

| Метод / путь | Вход | Выход / ошибки |
|---|---|---|
| GET `/api/game/playtest-survey` | profile_id: positive int, survey_key=v2 для текущего клиента; без параметра v1 | 200: survey_key, profile_id, state pending/dismissed/submitted, closed_turns, should_offer, can_submit |
| POST `/api/game/playtest-survey/dismiss` | profile_id, survey_key=`first_turns_v2` | 200: то же состояние; повтор идемпотентен, submitted не откатывается |
| POST `/api/game/playtest-survey` | profile_id, survey_key, answers (девять ключей), comment="" | 200: submitted state, response_id; идентичный повтор возвращает тот же ID; изменённый повтор 409 |
| GET `/api/admin/playtest-surveys` | limit 1…200, default 50 | Только admin, 200: submitted rows, по убыванию даты; 403 обычному пользователю |

Игровые методы требуют get_current_user. profile_id проверяется на ownership;
чужой/несуществующий — 404 без раскрытия существования. Plan — 410.
Без начатой партии — 404; не создавать fallback профиль ради опроса.
Неверные enum/version/поля, пропуск ответа, комментарий >1000 — 422.
Не доверять user_id/снимку прогресса от клиента: лишние поля запрещены.
Сериализация на пользователя + UNIQUE защищают конкурентный submit/dismiss;
при гонке dismiss не перезаписывает submitted. Повтор после потери ответа
сервера возвращает исходный ID без дублирования.

Аддитивное поле bootstrap `playtest_survey` (nullable, default null)
позволяет обновлять доступность без отдельного GET на каждый ход.
Старый frontend игнорирует поле; новый обрабатывает null как «не показывать».
Методы frontend в api/game.js, состояние/refresh в useGame; domain helper
показа не дублирует серверный подсчёт закрытий.

Админ-ответ: id, survey_key, game_profile_id, template_key, period_index,
closed_turns, answers, comment, submitted_at. Нет username/email/Telegram.
Доступ — существующий require_admin_user. Текст не попадает в обычные логи.
Watchtower использует текущую таблицу/панель и отдельный раздел «Опрос»;
существующие отзывы после финала не смешиваются с анкетами.

## UI и утверждение

Текущая группировка v2 в одном окне:
1. Деньги и подушка: зарплата, разница счёта и подушки.
2. Запас на расходы: переводы в подушку/обратно и запас денег на счёте.
3. Завершение хода: прогноз списаний, понятность итогов, затруднения.
4. Твои впечатления: сложность и желание продолжить.
5. Твой отзыв: необязательный свободный текст; пустой текст не мешает отправке.

Варианты сложности стоят в трёх равных колонках, radio над подписью: длинное
«Нормально» не выталкивает соседние ответы на 360 px.
Общие состояния: приглашение, пусто, ответы/disabled, sending, error,
success; light/dark, узкий и широкий viewport, клавиатура и radio labels.
Нужны focus trap/restore, Escape и scroll-lock по существующему MQX sheet.
Пункт меню и раздел Watchtower входят в этот же lab-срез.

Выбор владельца принят до переноса в MQX/приложение по
[DESIGN_WORKFLOW](../../../../frontend-react/src/components/mqx/DESIGN_WORKFLOW.md).
Доступен и в меню партии, и в меню сохранений: завершённую партию не нужно
активировать, чтобы ответить. При resync новые события и финал ждут закрытия
опроса; ответы не теряются из-за открытия другого оверлея.

5. Backend pytest, FE unit/build/guardrails и E2E на mobile/desktop.
   PostgreSQL migrate/repeat — на разрешённом изолированном стенде; при

Откат: отключить приглашение/меню в frontend; таблицу с ответами не удалять,
API additive. План не включает рассылку, публикацию или реальные ответы.

## Критичные сценарии

| ID | Проверка |
|---|---|
| CS1 | 4 закрытия — нет приглашения; 5 — доступно; period_index без closings не даёт приглашения |
| CS2 | После пятого close сначала итоги, потом приглашение; события/финал/guidance не перекрываются |
| CS3 | Позже + reload/другая партия — нет auto; меню доступно |
| CS4 | Девять ответов + пустой comment → сохранение, server snapshot, статус в bootstrap, одна запись |
| CS5 | Потеря ответа сети + повтор/двойной клик — один ID; changed payload → 409 |
| CS6 | 401 без auth; 404 чужой профиль; 422 invalid/extra; 403 admin endpoint обычному пользователю |
| CS7 | Ошибка сети оставляет draft; закрытие/профиль/возврат клавиатурного фокуса работают |
| CS8 | Watchtower показывает ответы и экранированный comment, без смешения с run_feedback |
| CS9 | Старые партии, проигрыш раньше P5, submission из меню до P5, null bootstrap и миграция |
| CS10 | Гонки submit/dismiss и два submit не теряют подтверждённый ответ |

Готово = утверждённый lab + контракт, реализация всех трёх шагов, проверки с
exit code, canon и обновлённый протокол волны. До этого фича не называется
встроенной в игру, а черновик не получает статус человеческого approval.
