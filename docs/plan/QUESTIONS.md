# PLAN — вопросы к обсуждению

Реестр для разбора с владельцем, а не новые требования. Источники: [spec](specs/SPEC_plan-v1.md), [роадмап](ROADMAP.md), [P3](plans/PLAN_plan-v1.md), [деплой](plans/PLAN_plan-deploy.md). Реальные данные, пользователи, письма и деплой этим документом не разрешаются.

## Решения владельца · 2026-11-03

Направления утверждены; реализация и приёмка впереди. Подготовка и рекомендации — [план базы](plans/PLAN_plan-foundation.md).

1. SPL-403: общий ui-kit делаем, api-client сохраняем. Нужны оба реальных потребителя примитивов; темы продуктов свои.
2. SPL-404: обзор текущей дизайн-системы и несколько lab-вариантов всего пути. C2 и U1/S4 сохраняют утверждение; новые варианты требуют выбора человека.
3. P3 после P2, исследование понятности параллельно. Уточнение владельца 2026-11-05: очередь P3-02 → P3-09 → P3-08 → P3-12; сначала lab состояний P3-02, затем API и UI после выбора варианта. Подробности — [план P3](plans/PLAN_plan-v1.md#очередь-владельца--2026-11-05).
4. Проверять синтетические кейсы несколькими способами, искать максимум недостатков. Программа — в плане базы; модератора и участников ещё нужно определить.
5. Для v1 достаточно e-mail-кода. Провайдер пока не выбран, отправка не разрешена, остаётся LogMailer.
6. Первый юридический срез — отдельная проектная AI-роль и подготовка базы. Роль пока не создана; подготовка не заменяет согласование юристом перед реальными пользователями и деплоем по ADR-017.
7. Начинаем с общепринятых финансовых критериев, затем выбираемые профили. Конкретные пороги, rules_version=2 и шесть месяцев всем семьям с детьми не утверждены: сначала источники и применимость.
8. Базовый обобщённый анализ инвестиций и защиты нужен; тексты и границы сохраняют юридический gate.
9. Описанные сценарии действий P3-02 и новые события P3-02/P3-09 утверждены. Payload требует минимизации данных; расширение событий согласуется отдельно.
10. Шаги, прогресс целей, история, сравнение и офлайн-отчёт нужны; сначала база. Точный состав первого релиза предстоит определить, дополнительные функции автоматически не утверждены.
11. Подготовить рекомендации по монетизации, затем корректировать. Предложение в плане базы; модель и цены пока не утверждены.
12. Домены, хостинг и эксплуатацию определяет владелец, сообщит отдельно. Деплой этим решением не разрешён.

## Решения 2026-11-09

Юридические пункты — рабочая позиция для разработки по вторичным источникам, а не заключение: тексты закона и выводы проверяет юрист (gate G1).

| Вопрос | Решение | Основание | Где в коде |
|--------|---------|-----------|------------|
| Вход для семьи | Один аккаунт на семью; отдельных входов нет. Если нужно, члены семьи входят под одной учётной записью (владелец, 2026-11-09). Два устройства одновременно — штатный случай | `households.user_id` уникален; ст. 9 152-ФЗ про согласие за третьих лиц — вопрос юристу | Запись черновика с `revision`, конфликт — 409 `checkup_changed`; один черновик на семью (`0002`) |
| Документы или таблицы | Оставляем JSON-документы с `schema_version`, таблицы — при конкретном SQL-сценарии. Закон формы хранения не задаёт; все чтения идут в рамках одной семьи | SPEC §Models расходится, отступление зафиксировано | `documents.py`, `0002` |
| `float` / `Decimal` | Ядро не переводим. Вход API — `Decimal` с двумя знаками; в JSON — число. Для всего диапазона `NUMERIC(14,2)` значение восстанавливается до копейки | CS-2; проверено 20 000 случайными суммами и границами | `test_money_survives_json_float_to_the_kopeck` |
| Хостинг и IP за прокси | Хостинг выбирает владелец (РФ, ст. 18 ч. 5). Число прокси задаётся явно, без него production не стартует | Лимиты и `consent_log` требуют адрес клиента | `PLAN_TRUSTED_PROXIES` |
| `localStorage`, шифрование | Норм про `localStorage` не найдено; финансовые данные не относятся к специальным категориям ст. 10. Шифрование БД напрямую не предписано: зависит от уровня защищённости (ПП 1119) и модели угроз. Прикладное шифрование не вводим. На хостинге — TLS и шифрование диска; для plan-web заголовок CSP | Подтверждает юрист вместе с моделью угроз | План деплоя |
| Настройки по умолчанию | Забытый `PLAN_ENV` на PostgreSQL останавливает старт; `dev_code` только на SQLite; код входа не пишется в логи production | Защита от входа в чужой аккаунт (ст. 19) | `settings.py`, `mailer.py` |
| Согласие | Production не стартует, пока `CONSENT_VERSION` — прототип. С 01.09.2025 согласие оформляется отдельно от других документов (ч. 1 ст. 9): нужен утверждённый текст и ссылка на него у галочки | Gate G1 | `settings.py` |

Остаётся юристу (G1): текст согласия и политики, данные членов семьи от третьего лица, уведомление Роскомнадзора, уровень защищённости и модель угроз, срок токена 30 дней и отчёт на устройстве, хранение `consent_log` после удаления аккаунта.

## Инженерные уточнения

- JSON `checkups.data_json` расходится с нормализованной моделью spec: сохранить документное хранение или нормализовать при появлении конкретного SQL-сценария? Решить до затрагивающего модель среза; P3-10 сам по себе не требует нормализации.
- Вопрос `float`/Decimal: P0 зафиксировал успешную сверку до копейки CS-2; общего перевода ядра это не разрешает. Нужен ли новый диапазон/кейс, где текущей точности недостаточно?
- В spec пути CS-тестов частично целевые: текущие тесты — `tests/test_api_flow.py` и `tests/test_analysis.py`; FE `npm run test:unit` добавлен 2026-11-04 для контрактов кнопок Game/Plan; он не закрывает целевое продуктовое покрытие P3-14. Не выдавать будущие файлы за уже доступное покрытие.

Уже решено: Plan — отдельный продукт; P2 не ждёт gate GAME (ADR-017); движок шагов/онбординга свой (P3-01); лозунг U1 «Деньги отвечают» и отчёт C2 утверждены. Повторного решения по этим пунктам не требуется.
