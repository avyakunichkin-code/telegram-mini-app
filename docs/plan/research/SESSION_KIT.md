# Первая проверка ПЛАНА · комплект ведущего

Подготовлено 07.11.2026 для 3–5 модерируемых сессий **варианта А**.
Сессии не проведены. Это подготовка локального исследования на вымышленном
кейсе, без публикации, приглашений, настоящих аккаунтов и финансовых анкет.
Применяется навык delivery; новые интерфейсы приложения не создаются.

## Что открыть

1. Ведущему: [сценарий и ответы](FACILITATOR_SCRIPT.md).
2. Участнику: только [карточку вымышленной семьи и задания](PARTICIPANT_CARD.md).
3. Наблюдателю: копию [бланка одной сессии](OBSERVER_FORM.md).
4. После сессий: [шаблон итогового решения](RESULTS_TEMPLATE.md).

Карточку можно показать отдельным файлом или распечатать. Ответы ведущего и
рубрику не показывать до самостоятельной части. В первой волне не сравнивать
А с неутверждённым Б. Проверяем приложение Plan, а не HTML из design-lab:
lab-плашка восстановления не проверяет сохранность ввода.

## Перед первым участником

- Выбрать работающий локальный стенд Plan на устройстве ведущего; не подключать
  production и не пересоздавать существующую БД. Если изолированного стенда нет,
  подготовку остановить до его создания, а не использовать неизвестные данные.
- Создать отдельный чистый контекст браузера для каждой сессии. Вход ведущий
  проходит заранее с вымышленным адресом session01@example.com и dev-кодом
  самого тестового стенда. Не просить участника вводить свою почту; код не отправлять.
- Оставить экран выбора вопроса, без готовой семьи и предзаполненного чекапа.
  Аккаунт для следующей сессии — другой вымышленный адрес/контекст. Существующий
  прогресс не удалять. «Заполнить демо-семьёй» не использовать: это другой кейс.
- Пройти сценарий самому на отдельном тренировочном контексте, сверить арифметику
  по ответам ведущего. Тренировку не считать результатом участника.
- Записать revision и метку локальной сборки: dirty checkout нельзя обозначать
  одним SHA. В отдельном файле вне git сохранить техническую запись проверенного
  состава, дату, frontend/backend, браузер и viewport. Между сессиями код не менять;
  при изменении сборки начать отдельную группу результатов.
- Объяснить добровольность участия. Не записывать экран/голос без отдельного
  согласия; для этого раунда достаточно категорий ошибок и отметок помощи.

## Как вести и записывать

Ориентир — 15–20 минут, не критерий успеха. Давать задания по одному.
Сначала самостоятельная попытка; помощь фиксировать отдельно. Если нет
продвижения около минуты, спросить, хочет ли человек подсказку. Не требовать
уложиться во время и не исправлять ответ до его фиксации.

Результаты сессий хранить в выбранном владельцем рабочем месте **вне репозитория**.
В git — только пустые шаблоны и явно синтетические fixtures. Не добавлять имена,
контакты, реальные суммы, цитаты с личными сведениями, записи или токены.
Для разбора хватает закрытых категорий и счётчиков. Адреса тестовых аккаунтов
и их идентификаторы в агрегат не переносить.

## Как получить агрегат

Скопировать [пустой JSON](observations.template.json) вне репозитория. Указать
метку проверенного build. После **завершённой или остановленной** сессии добавить
одну запись по схеме из бланка; не заводить заранее пять строк-заглушек.
Пропущенные задания — unobserved, не ошибка. Прерванная сессия остаётся в числе
сессий, задания без наблюдения видны отдельно.

Из корня проекта, где `$observationPath` — абсолютный путь выбранного JSON:

```powershell
$observationPath = Read-Host 'Полный путь к обезличенным отметкам вне репозитория'
node scripts/plan-understanding-report.mjs $observationPath
```

Утилита выводит только агрегат в stdout. `synthetic` — искусственный fixture,
всегда human_evidence=false. `synthetic_case_observations` — отметки наблюдателя
о работе человека с **вымышленной** семьёй; human_evidence=true только при n>0.
Этот флаг описывает источник записей, не подтверждает качество исследования.
Агрегатор не проверяет правдивость заполненных отметок и не принимает сырые анкеты.

Проверка инструмента без участников:

```powershell
node --test scripts/plan-understanding-report.test.mjs
node scripts/plan-understanding-report.mjs docs/plan/research/observations.template.json
node scripts/plan-understanding-report.mjs docs/plan/research/understanding.synthetic.json
```

Приоритет следующей итерации: воспроизводимая потеря данных/ошибка расчёта,
затем неверное понимание перевода или вывода, затем навигация и тексты.
Данные 3–5 сессий не доказывают конверсию или причинное улучшение финансов.
Серверная воронка P3-10 остаётся отдельным срезом.
