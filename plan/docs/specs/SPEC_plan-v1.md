# Spec: ТВОЙ ПЛАН v1 — семейный финансовый чекап

**Продукт:** «ТВОЙ ПЛАН. Деньги отвечают.» (лозунг утверждён 2026-11-02, [`design-lab/plan-checkup`](../../design-lab/plan-checkup/APPROVED.md)). Отдельное приложение, не режим игры ([ADR-016](../../../docs/decisions/ADR-016-two-products-shared-fincore.md)). Общее с игрой — только `shared/packages/fincore` и `shared/packages/platform`.

**Статус:** approved владельцем продукта 2026-10-26.

**Gate реализации (ред. 2026-10-27, D4):** **рабочий прототип** (`apps/plan-api`, `apps/plan-web`) — сейчас: только поверх `fincore`, хранилище в памяти, код входа в ответе (`dev_code`), без деплоя и реальных пользователей. **Продуктовая реализация** — своя БД `plan`, реальный вход (SPL-402+) — с 2026-11-02 без Pre-Alpha gate игры, после SPL-302 ([ADR-017](../../../docs/decisions/ADR-017-plan-p2-without-game-gate.md)). Реальные пользователи, хостинг в РФ и деплой — после юриста и решения PO. Роадмап — [`ROADMAP.md`](../ROADMAP.md).

## Assumptions

1. **Каналы:** PWA/web (`apps/plan-web`, Vite + React), без Telegram Mini App в v1.
2. **Валюта и гранулярность:** только рубли; время — календарные месяцы. Адаптер Plan переводит `YYYY-MM` в `month_index` ядра.
3. **Вход:** e-mail + одноразовый код (без пароля). Telegram Login — открытый вопрос ([#1](#open-questions)).
4. **Хостинг и данные:** контур РФ, своя БД PostgreSQL `plan`; Plan — оператор ПДн по 152-ФЗ.
5. **Члены семьи** — профили внутри одного аккаунта: метка («Я», «Партнёр», «Ребёнок 1») и роль, **без ФИО**. Год рождения необязателен.
6. **Прогноз «если ничего не менять»:** без инфляции и индексации доходов (как `fincore.forecast`). Инфляция — только в стресс-сценарии.
7. **Пороги светофора и параметры сценариев — предварительные.** Они хранятся в версионируемом конфиге правил (`rules_version`) и калибруются до α Plan.
→ Поправьте до начала реализации.

## Objective

**Why:** пара или семья не видит целиком, где она сейчас, что её сломает и с чего начать. Трекеры расходов отвечают на вопрос «куда ушли деньги», банковские калькуляторы — на один частный вопрос. Plan за один вечер даёт честный разбор семьи и стресс-тест её устойчивости.

**Who:** пары и семьи 28–45 лет: два дохода, ипотека или кредиты, дети или планы на детей. Учёт ведёт один человек.

**Success criteria:**

Продуктовые (замер — собственные события Plan, см. [Аналитика](#аналитика-продукта)):

- [ ] **≥ 50 %** начавших чекап (`checkup_started`) получают итоговый отчёт (`report_viewed`, `final=true`).
- [ ] **≥ 30 %** получивших отчёт отмечают хотя бы один шаг выполненным в течение 30 дней (`step_done`).
- [ ] Черновой отчёт после быстрого старта — за **≤ 3 минуты**, медиана; полный чекап — за **≤ 20 минут**, медиана.

Технические:

- [ ] Прогноз и стресс-тесты считает `fincore` (`month_step` / `next_snapshot` / `forecast`); формул движения денег в Plan нет.
- [ ] Сверка до копейки: сумма проводок за месяц равна изменению `cash` на каждом месяце прогноза (CS-2).
- [ ] Отчёт детерминирован: одинаковые данные + `rules_version` + версия fincore дают одинаковый отчёт (CS-5).
- [ ] `GET .../report` укладывается в **p95 ≤ 1 с** (12 месяцев прогноза, 4 сценария, ≤ 8 членов семьи, ≤ 50 строк на раздел).
- [ ] Удаление аккаунта уничтожает данные пользователя не позже чем через 30 дней (152-ФЗ, ст. 21) (CS-8).

## Scope

### In scope

- Аккаунт по e-mail, согласие на обработку ПДн, удаление аккаунта.
- Одно домохозяйство на аккаунт; члены семьи — профили.
- **Вопрос на входе** (5 вариантов) задаёт порядок ввода и главный блок отчёта.
- **Быстрый старт:** 5 вопросов с ответами диапазонами → черновой отчёт.
- **Уточнение по разделам:** доходы, расходы, долги, накопления и подушка, имущество, инвестиции (по классам активов), пенсия, страховки, цели. Значение вводится точно или диапазоном.
- **Итоговый отчёт:** ответ на вопрос со входа, светофор по 4 областям, ключевые метрики, net worth, прогноз на 12 месяцев (базовый и пессимистичный), стресс-тест на 4 сценариях, стратегия гашения долгов, реалистичность целей, **3 шага** с объяснением «почему».
- Отметка шага: «сделано» или «не подходит».
- Повторный чекап — новая версия на основе прошлой; история отчётов.
- Собственная продуктовая аналитика: воронка и шаги.

### Out of scope

- PDF «Семейный совет» → v1.1.
- Ежемесячное ведение (факт против плана) и годовой отчёт семьи → v2.
- Пользовательские параметры сценариев и свои сценарии.
- Импорт выписок, подключение банков, совместный доступ нескольких аккаунтов.
- Конкретные ценные бумаги, «купи/продай», подбор продуктов и партнёрские предложения.
- LLM-советник, игровые механики, общий аккаунт с игрой, TMA, контур ЕС.
- Монетизация (решается при детальном планировании).

## User flows

| Step | Actor | Result |
|------|-------|--------|
| 1 | Гость открывает лендинг, вводит e-mail | На почту приходит 6-значный код (TTL 10 мин) |
| 2 | Вводит код, принимает согласие на обработку ПДн | Аккаунт, JWT Plan (`iss=plan`), запись в `consent_log` |
| 3 | Выбирает вопрос: «Потянем ли ипотеку/крупный кредит?», «Когда закроем кредиты?», «Выдержим ли, если что-то случится?», «Успеем ли накопить на цель?», «Как у нас дела в целом?» | Черновик чекапа `checkup` с `entry_question` |
| 4 | Добавляет членов семьи (метка, роль, взрослый/ребёнок) | Профили; по умолчанию один «Я» |
| 5 | Быстрый старт: доход семьи, обязательные расходы, платежи по кредитам, накопления, число детей — диапазоны или пресеты | **Черновой отчёт**: светофор, прогноз и шаги с пометкой «точность: черновая» |
| 6 | Уточняет разделы (мастер, порядок задан вопросом со входа). Например, для «ипотеки» сразу просим цену, первый взнос, ставку и срок | После каждого раздела черновой отчёт пересчитывается; точность растёт |
| 7 | Нажимает «Получить итоговый разбор» | `complete`: отчёт сохраняется с `rules_version`; `report_viewed final=true` |
| 8 | Читает отчёт, отмечает шаг | `step.status=done`; событие `step_done` |
| 9 | Возвращается через N месяцев: «Пересчитать» | Новый черновик = копия последнего чекапа; старые отчёты не меняются |
| 10 | Профиль → «Удалить мои данные» | `users.deleted_at`, вход заблокирован, данные уничтожаются в ≤ 30 дней |

## Data & API

### Время и месяц

`month_index = (year − 2000) × 12 + (month − 1)`. Отчёт строится на месяц `as_of`, в котором завершён чекап. Цели и сроки задаются как `YYYY-MM`.

### Ввод диапазонами

Каждое денежное поле — пара `amount_min` / `amount_max` (точное значение: `min = max`). Из одного чекапа собираются два снимка ядра:

| Снимок | Доходы | Расходы и платежи | Накопления |
|--------|--------|-------------------|------------|
| **base** | середина | середина | середина |
| **pessimistic** | `min` | `max` | `min` |

**Точность отчёта** = доля денежных полей с `max / min ≤ 1.1` среди заполненных, взвешенная по сумме. Пороги: `черновая` < 50 % ≤ `приблизительная` < 85 % ≤ `уточнённая`.

**P3-11, UI A утверждён 2026-11-07:** мастер показывает предварительную оценку на каждом разделе и предлагает сначала уточнить раздел с наибольшим неточным весом. Вес диапазонов — верхняя граница; оценённых кредитов — платёж, как в существующем `adapter.precision`. Пустой набор обозначается «Нет сумм для оценки». Широкий диапазон (`max/min > 3`, либо `min=0<max`) даёт предупреждение без запрета сохранения. Это оценка заполнения денежных данных, не вероятность прогноза и не подтверждение полноты анкеты. Источник UI — [precision-round/APPROVED.md](../../design-lab/plan-checkup/precision-round/APPROVED.md); реализация — `plan/web/src/precision.js`, `src/screens/precision/` и `Refine.jsx`. Сохранённый отчёт остаётся серверным.

### Адаптер Plan → fincore

| Plan | fincore |
|------|---------|
| `incomes` | `Income(monthly_amount, member_id)` |
| `liabilities` | `Liability` (kind, payment_mode, term_months, overdue; `member_id`) |
| `expense_lines` | `ExpenseLine(category_key, amount_monthly, tier)` |
| `savings` с `is_safety_fund` | `HouseholdSnapshot.safety_fund` |
| `savings` (cash/account) | `cash` |
| `savings` (deposit) | `InvestmentPosition(principal, annual_rate_percent)` |
| `assets` | `Asset(value, monthly_maintenance, monthly_income)` |
| `investments` | `Asset(kind=f"invest:{asset_class}", value)` — для net worth, без доходности в прогнозе |
| `insurance` | `InsurancePolicy(monthly_premium, coverage_limit)` |
| `pension`, `goals`, `members` | не в ядре — слой анализа Plan |

**Изменение fincore (единственное):** опциональное поле `member_id: int | str | None = None` в `Income` и `Liability`. Игровой адаптер его не заполняет. Golden-тесты игры и balance diff должны остаться = 0 (CS-10).

### Расчёт отчёта (слой анализа Plan, `plan/api/app/analysis/`)

1. **Метрики** — `fincore.compute_metrics` на base и pessimistic: DTI (`liabilities_to_income_percent`), норма сбережений `= net_structural_cashflow / income_steady`, `safety_fund_months`, `net_worth`, `total_overdue`.
2. **Прогноз 12 месяцев** — `fincore.forecast(credit_income=True)` для base и pessimistic: ликвидность по месяцам, месяц первого ухода в минус.
3. **Стресс-сценарии** — цикл `month_step` → `next_snapshot` с модификатором снимка по месяцам, 12 месяцев, на base:

   | ID | Сценарий | Модификатор (параметры в конфиге правил) |
   |----|----------|-------------------------------------------|
   | S1 | Потеря крупнейшего дохода | доход члена с макс. доходом = 0 на 6 мес. |
   | S2 | Рождение ребёнка | +`child_monthly_cost` расходов; доход одного взрослого −`parental_leave_cut` % на 12 мес. |
   | S3 | Рост цен | расходы `must` и `want` +10 % |
   | S4 | Решение со входа | для «ипотеки»: новый аннуитет `fincore.annuity` (цена − взнос, ставка, срок), взнос списывается из ликвидности; для остальных вопросов — S4 = комбинация S1 + S3 |

   Итог сценария: `months_until_negative` (или «> 12»), минимальная ликвидность и вердикт `ok` (ликвидность ≥ 0 все 12 мес.) / `edge` (минус ≤ 1 мес. расходов) / `fail`.
4. **Стратегия долгов** — три графика до полного погашения: «как сейчас», «лавина» (сверх платежа на максимальную ставку), «снежный ком» (на минимальный остаток). Сумма сверх платежа по умолчанию = 50 % положительного свободного потока после взноса в подушку; итог — дата закрытия и переплата.
5. **Цели** — нужный взнос в месяц `= (target − saved) / месяцев_до_срока`, сравнение со свободным потоком. Если не хватает — реалистичный срок.
6. **Светофор** (пороги предварительные, `rules_version=1`):

   | Область | Зелёный | Жёлтый | Красный |
   |---------|---------|--------|---------|
   | Бюджет | норма сбережений ≥ 10 % | 0–10 % | < 0 |
   | Долги | DTI < 30 % и нет просрочки | DTI 30–50 % | DTI > 50 % или просрочка > 0 |
   | Подушка и цели | подушка ≥ цели* и цели реалистичны | подушка 1 мес. – цель* или цель нереалистична | подушка < 1 мес. |
   | Инвестиции и защита | нет флагов | ≥ 1 флага | — (в v1 красного нет) |

   \* Цель подушки: 3 мес. расходов; 6 мес., если в семье есть ребёнок и один доход даёт > 70 % дохода семьи.

   Флаги «инвестиций и защиты»: инвестиции > 0 при подушке ниже цели; один класс активов > 50 % портфеля; неликвидные (`years`) активы при цели в ближайшие 12 мес.; ипотека без `life`/`mortgage_title`; ребёнок и единственный кормилец без `life`; у взрослого старше 35 нет пенсионных накоплений.

7. **Шаги** — детерминированные правила по приоритету. Берутся три первых сработавших, не больше одного на правило:

   | Приоритет | rule_key | Условие | Текст (шаблон) |
   |-----------|----------|---------|----------------|
   | 1 | `close_overdue` | просрочка > 0 | Закрыть просрочку {title} — {amount} ₽: штрафы и кредитная история |
   | 2 | `stop_deficit` | свободный поток < 0 | Сократить расходы на {gap} ₽/мес; крупнейшие статьи «по желанию»: {top3} |
   | 3 | `first_cushion` | подушка < 1 мес. | Отложить {amount} ₽ — месяц расходов, первая ступень подушки |
   | 4 | `avalanche` | долг со ставкой > 20 % и подушка ≥ 1 мес. | Гасить досрочно {title}: экономия {saved} ₽, закрытие на {months} мес. раньше |
   | 5 | `stress_fail` | S1 или S4 = `fail` | {scenario}: деньги кончатся через {n} мес.; нужна подушка {target} ₽ |
   | 6 | `goal_unrealistic` | цель нереалистична | Сдвинуть «{goal}» на {date} или откладывать {monthly} ₽/мес |
   | 7 | `cushion_target` | подушка < цели | Довести подушку до {target} ₽: {monthly} ₽/мес — {months} мес. |
   | 8 | `protection_check` | флаг страхования | Проверить, что защищён доход семьи при ипотеке/детях (страхование жизни) |
   | 9 | `liquidity_first` | инвестиции при подушке ниже цели | Сначала подушка: часть вложений неликвидна в нужный срок |
   | 10 | `concentration` | один класс > 50 % | Обсудить распределение вложений со специалистом |
   | 11 | `direct_surplus` | всё зелёное | Направить свободные {amount} ₽/мес на «{goal}» |

   «Почему» — это всегда числа из метрик, которые сработали в условии. Тексты правил 8–10 согласуются с юристом.

### Endpoints (`apps/plan-api`, префикс `/api`)

Ошибки, идемпотентность и health — из `shared/packages/platform`. Все `/api/*`, кроме auth и health, требуют JWT Plan (`iss=plan`, `aud=plan-web`). Ресурсы чужого домохозяйства → **404**.

### Аналитика продукта

События (`product_events`): `signup`, `consent_accepted`, `checkup_started {entry_question}`, `quick_done {duration_seconds}`, `section_done {section}`, `report_viewed {final, precision}`, `checkup_completed {duration_seconds}`, `step_done {rule_key}`, `step_dismissed {rule_key}`, `step_action_done {rule_key, action}`, `account_deleted`. Сторонних аналитических SDK в v1 нет: финансовые данные и ПДн не уходят из контура РФ.

Контракт P3-09 (2026-11-05):

| Событие | Только разрешённые props |
|---|---|
| signup / account_deleted | `{}` |
| consent_accepted | `{consent_version}` — текущая фиксированная версия согласия |
| checkup_started | `{entry_question}` — enum вопроса |
| quick_done / checkup_completed | `{duration_seconds}` — строго целое неотрицательное число от сервера |
| section_done | `{section}` — enum раздела |
| report_viewed | `{final, precision}` — строго boolean и enum точности |
| step_done / step_dismissed | `{rule_key}` — ключ существующего правила |
| step_action_done | `{rule_key, action}` — ключ правила и ключ его действия из config |

Неизвестные поля, свободный текст и финансовые значения запрещены для всех
источников, включая внутренний `Repo.track`. Проверка по схеме заменяет старый
критерий «любое число > 1000»: 1200 секунд — допустимая длительность, а сумма
даже 1 ₽ не является допустимым полем. Строгость проверяется до записи в БД.

Секунды считаются по серверным UTC `checkups.created_at` → успешное сохранение
quick / `completed_at`; это календарная длительность, включая паузы и возвраты,
не время активного внимания. Возобновление черновика не сбрасывает начало.
Первое успешное сохранение quick и каждого раздела фиксируется один раз на чекап,
повторные сохранения не дублируют milestones; следующий чекап имеет свой отсчёт.
Отрицательная разность при сдвиге часов ограничивается нулём. Старые события без
длительности сохраняются без выдуманного backfill и не дают измерения времени.

`report_viewed` означает успешную **выдачу** отчёта API: GET, завершение и выдачу
сохранённого результата по idempotency key. Это не подтверждение прочтения.
Повторное открытие создаёт новое событие просмотра, завершение чекапа — одно.
Потребители `plan/web/src/api.js` уже используют эти маршруты; клиентский
таймер и дополнительная отправка событий не нужны.

`POST /api/events` требует JWT и поддерживает только `report_viewed` с указанной
схемой (204). Остальные имена остаются в серверном каталоге, но клиентская отправка
отклоняется 422 `server_event_only`; неизвестное имя/props также → 422, без JWT → 401.
Это сужение прежнего произвольного props-контракта; текущих frontend-вызовов
`/api/events` нет. Нельзя подделать клиентом длительность или факт выполнения шага.

При удалении аккаунта его `product_events` удаляются сразу в той же транзакции,
токен отзывается. Сохраняется только `account_deleted` с `user_id=NULL`, props `{}`
и временем события, без связующего идентификатора. Последующий purge не удаляет
события других пользователей. Внешних SDK, новой таблицы или миграции нет.

## UI / UX

### P3-12 · последний итоговый отчёт офлайн (2026-11-05)

В production-сборке собственный service worker сохраняет только оболочку
(HTML и собранные JS/CSS), по allowlist. API, токены и финансовые ответы в
CacheStorage не попадают. Dev-сервер service worker не регистрирует.

Последний полученный итоговый отчёт сохраняется отдельно, в локальном снимке
`plan.last-report.v1`. Сохраняются отчёт, id/месяц/дата завершения чекапа,
время копирования и начальный запас для существующего графика. Исходная анкета,
состав семьи, e-mail и дополнительная копия JWT не сохраняются. В снимке есть
данные финансового отчёта; это локальное хранилище текущего origin браузера.
Снимок привязан к проверенному пользователю и SHA-256 текущего токена сессии.
Другая сессия, другой пользователь, истёкший токен, несовместимая/повреждённая
схема исключают чтение. Без завершённого отчёта доступна только явная ошибка
«Нет сети и сохранённого итогового отчёта», без создания фиктивных результатов.

Офлайн открывается существующий экран отчёта: месяц данных остаётся в шапке,
там же текст «Офлайн · только чтение · копия сохранена {дата и время}».
Новый layout не вводится. Отметки действий, ручные статусы, новый чекап и
удаление аккаунта недоступны до подключения; выхода из аккаунта это не касается.
Черновик не кэшируется. Старый открытый отчёт не вытесняет более поздний
завершённый; обновление отметок того же отчёта обновляет снимок.

Снимок очищается при выходе, смене токена/аккаунта, успешном удалении аккаунта
и наблюдаемом 401. Отмена или ошибка удаления не выдаётся за удаление аккаунта.
Отложенная запись не может восстановить снимок после выхода; другие открытые
вкладки сбрасывают данные по storage event. Статическая оболочка без финансовых
данных может оставаться, чтобы показать вход без сети.

При возвращении сети приложение проверяет сессию через API и возвращается
к серверным данным. HTTP-ошибка авторизации не подменяется офлайн-копией.
Удалённый на другом устройстве аккаунт нельзя проверить без сети: наблюдаемое
отзывание проверяется при подключении. Длительность автономного доступа
ограничена сроком текущего токена. Внешних зависимостей и отправки данных нет.

### Экраны и оформление

P3-07 (2026-11-06, утверждён B «Маршрут цели» с поздравлением): `GoalRow.id`
nullable для legacy, для новых целей выдаётся сервером при PUT секции; ID сохраняется
при правках и повторном чекапе. Дубли и неизвестный присланный ID дают 422,
чужой чекап — 404. Отсутствующий `target_month=null` разрешён: нужный взнос и
реалистичность срока неизвестны, предлагается добавить срок. JSON-хранение прежнее.

Новые отчёты включают `id`, `saved_amount` и `progress` в каждой цели. `progress`:
status (new/compared/unavailable), before/delta/months/before_as_of,
observed_monthly/estimated_month/previous_estimated_month, previous_target_amount,
target_changed, achieved. Сравнение только по ID с сохранёнными goals собственного
завершённого родителя. Legacy без ID не сопоставляется по названию или позиции.
Старый отчёт не пересчитывается; контекст нового final сохраняется и не меняется
при чтении или идемпотентном завершении, старые final не дополняются задним числом.

Темп — Δ saved_amount / число календарных месяцев между as_of. При том же месяце
темп null; при нулевом/отрицательном темпе нет прогнозной даты. Оценка по темпу:
as_of + ceil(остаток / неокруглённый темп); округление суммы для показа не сдвигает
дату. Дата за пределами четырёхзначного года неизвестна. Это сценарий без доходности,
не обязательство. Свободный остаток не считается взносом каждой цели. Изменение
target_amount показано явно; старая оценка остаётся сохранённой. Достижение означает
saved_amount >= target_amount: медаль, поздравление и завершённый маршрут вместо
прогноза, без утверждения покупки. Второстепенные цели раскрываются. Офлайн читает
сохранённый блок в составе P3-12; старые final без progress сохраняют таблицу.

P3-03 (2026-11-06, владелец выбрал 3 «Мост между шагами»): новый GET draft report
и POST complete добавляют `previous_steps`. DTO: status=none|ready|unavailable,
steps (массив); при ready — parent_checkup_id, as_of, completed_at, versions_differ.
Каждый прошлый шаг содержит id, rule_key, title, status, rank, actions_total и
actions_done (integer|null для legacy), metric (object|null). Метрика содержит
key/title/unit/before/after/delta с number|null, как в сравнении истории.

Родитель — строго parent_checkup_id; перед чтением проверяются household и completed.
Нет родителя → none, отсутствует/чужой/нет снимка → unavailable с пустыми steps,
без чужих данных. Старый report не пересчитывается. В черновике берутся актуальные
статусы родителя; при complete контекст сохраняется в новом JSON. Последующий
GET final/idempotent complete не обновляет его из изменённых родительских шагов.
Старые final без поля previous_steps не дополняются задним числом.

Основной шаг выбирается детерминированно: done → с отмеченными действиями →
неотмеченное suggested → dismissed; внутри группы исходный rank. Непринятое
предложение не называется «выбрали». first_cushion/cushion_target/stress_fail
сравнивают сохранённые месяцы подушки; stop_deficit/direct_surplus — остаток;
avalanche — DTI (дельта в п. п.). Для остальных правил metric=null: числовой
результат не выдумывается. Новые финансовые правила/пороги и события не вводятся.
Мост показывает прошлое рядом с текущим билетом, остальные прошлые шаги раскрываются.
Отметки прошлого шага не переносятся на новые действия; изменение данных не
приписывается автоматически выполнению шага. Офлайн прошлый контекст читается
из последнего снимка P3-12, открытие прежнего отчёта disabled.

P3-08 (вариант 2 «Журнал с полями», явное утверждение владельца в чате;
внедрение 2026-11-06): профиль содержит историю завершённых чекапов и отдельный
переход к черновику. Сравниваются сохранённые 4 области и 5 метрик:
free_cashflow, metrics_base.safety_fund_months, metrics_base.dti_percent,
metrics_base.total_debt, net_worth. Дельта DTI — процентные пункты, не проценты
роста. Пропущенная метрика и её дельта — null, UI не подставляет ноль.

`GET /api/checkups` сохраняет прежние поля и добавляет question (string|null),
report_available (boolean), areas (массив key/title/light|null), rules_version
(сохранённая версия|null). Черновики идут отдельно, завершённые — по дате
завершения от новых к старым; новые временные метки создания/завершения сохраняют
микросекунды, чтобы несколько чекапов за секунду не упорядочивались по случайному id.

`GET /api/checkups/{current_id}/compare/{previous_id}` требует пользовательский
JWT и владение **обоими** чекапами; чужой/несуществующий → 404, без входа → 401.
Оба должны быть разными completed, previous не позже current; нарушение → 422.
Нет сохранённого отчёта → 409 report_unavailable, без регенерации. Открытие такого
завершённого отчёта через прежний GET report также возвращает 409.

Ответ сравнения: before/after с checkup_id, entry_question, question,
as_of, completed_at, rules_version, fincore_version и areas; versions_differ
(boolean); metrics (5 объектов key/title/unit/before/after/delta).
unit — rub/months/percent, значения number|null; delta — after-before или null.
versions_differ учитывает правила и версию ядра: числа можно читать, но UI
предупреждает о возможной смене значения цвета. GET не вызывает build_report,
не изменяет сохранённые расчёты, не создаёт новых событий аналитики.

История доступна при подключении. Без сети остаётся последнее итоговое чтение
P3-12, сравнение и загрузка старых отчётов не имитируются. Открытие старого отчёта
не вытесняет более позднюю офлайн-копию. В UI предусмотрены loading/empty/error,
повтор загрузки списка и сравнения, один отчёт, отсутствующие метрики и разные версии.

- **Экраны `apps/plan-web`:** лендинг и вход по коду → согласие → выбор вопроса → члены семьи → быстрый старт → черновой отчёт → мастер уточнения (прогресс по разделам, на каждом шаге «точно / примерно от–до») → итоговый отчёт → профиль (история, удаление данных).
- **Отчёт сверху вниз** (ред. 2026-11-04, утверждённые C2 + M1/F2/A2/S1 из [`design-lab/plan-checkup`](../../design-lab/plan-checkup/APPROVED.md)): светофор 2×2 → прогноз двумя дорожками base/pessimistic (F2) → ответ на вопрос в заметке A2 и первый шаг S1 рядом, на телефоне последовательно → остаток в месяц и точность → подробности с мерным стаканом подушки M1 → остальные шаги → стресс-тесты с графиками → долги → цели. Все показатели и рекомендации — из данных чекапа/API; иллюстративные суммы и пороги lab не являются правилами. Бейдж точности в шапке; дисклеймер внизу.
- **Тон:** спокойный, без игровой эстетики и без запугивания. Красный цвет — только для фактов (просрочка, минус), не для оценки людей.
- **Бренд:** свои токены; из `shared/packages/ui-kit` — только примитивы (SPL-403). Раунд lab — `plan/design-lab/plan-checkup/` (SPL-404), лозунг — ★ «Деньги отвечают» (2026-11-02).
- Состояния: loading / empty / error на каждом экране; офлайн — только чтение последнего отчёта (PWA-кэш).

## Rules & edge cases

- `amount_min > amount_max` → 422; `max / min > 3` → предупреждение в UI, не ошибка.
- Нулевой доход: отчёт строится, норма сбережений = n/a, «Бюджет» = красный, первый шаг — `stop_deficit`.
- Карта без срока: `term_months_left = null`, `payment_mode` — минимальный платёж; лавина и снежный ком считают до нуля, но не дольше 360 мес. (иначе «не гасится при текущем платеже»).
- Платёж меньше процентов → долг растёт; флаг в «Долгах», шаг `stop_deficit` или `avalanche`.
- Ипотека со входа: взнос > ликвидности → вердикт S4 = `fail` с текстом «не хватает на взнос {gap} ₽».
- Члены семьи: ≤ 8; у `child` нет доходов и долгов (422).
- Завершённый чекап неизменяем; правка → новый черновик.
- Старые отчёты не пересчитываются при смене `rules_version`; в отчёте видна версия.
- В логах нет сумм вместе с `user_id`/e-mail; e-mail в логах маскируется.
- Дисклеймер в каждом отчёте: информационный расчёт на данных пользователя, не индивидуальная инвестиционная рекомендация.
- Повторный `complete` с тем же `Idempotency-Key` → тот же отчёт; без ключа на `completed` → 409.

## Boundaries

- **Always:** все расчёты движения денег — через `fincore`; суммы `Decimal`/`NUMERIC` на границе API и в БД; правила и пороги — в версионируемом конфиге (`rules_version`); у каждого шага «почему» с числами; дисклеймер в отчёте; изоляция по `household_id` в каждом запросе.
- **Ask first:** любые изменения DTO `fincore`, кроме `member_id`; новые зависимости (почтовый провайдер, PDF); смена порогов светофора и параметров сценариев; новые события аналитики; тексты правил 8–10 и согласия (через юриста).
- **Never:** импорт `app.*` игры и игровые понятия (ход, потребности, события, победа); тикеры, эмитенты, «купи/продай»; LLM-генерация советов; ФИО и реквизиты в модели; отправка ПДн и финансовых данных сторонним сервисам вне контура РФ; суммы в логах вместе с идентификатором пользователя.

# Уточнение P3-02 · 2026-11-05

Утверждён компактный B в `plan/design-lab/plan-checkup/actions-round/`.
Существующие финансовые правила и версия расчёта не меняются.

- Новый отчёт добавляет к каждому шагу `actions: [{key: string, title: string, done: boolean}]`.
  Для правил 1–7 и 11 — 1–3 действия из `plan_api/analysis/config.py`; правила 8–10
  пока возвращают пустой список. Действия и тексты фиксируются при сохранении отчёта.
- `PATCH /api/steps/{id}/actions/{key}` принимает `{done: boolean}` (строго boolean),
  возвращает полный обновлённый шаг с `actions`, `status`, `status_at` (ISO UTC).
  Тот же результат доступен при повторном чтении отчёта. JWT и household isolation
  обязательны; отсутствующий/чужой шаг или неизвестный key → 404; неверный body → 422;
  нет авторизации → 401; конфликт обновлений/закрытый шаг → 409.
- Повтор установки уже сохранённого значения идемпотентен, событие не дублируется.
  Последняя отметка завершает шаг автоматически. В `step_action_done` только
  `rule_key` и `action` (стабильный key), без заголовков, сумм и содержимого анкеты.
  Автоматическое завершение также создаёт существующее событие `step_done`.
- Ручные done/dismissed сохраняют частичные отметки. Для изменения закрытого шага
  нужен возврат в suggested; если все действия выполнены, возврат снимает последнюю
  отметку. Снятие отметки в открытом шаге сохраняется без события выполнения.
- Прогресс хранится в существующем JSON шага; исходный payload расчёта отчёта
  не меняется. Старые отчёты без actions не пересчитываются, ручные статусы доступны,
  PATCH несуществующего действия возвращает 404. Новая схема SQL не требуется.
- UI показывает один счётчик в summary, вертикальный список и крупные чекбоксы;
  черновик и offline запрещают запись, ошибка оставляет подтверждённый прогресс
  и предлагает повтор. Онлайн-приложение подтверждает отметку только ответом API.
