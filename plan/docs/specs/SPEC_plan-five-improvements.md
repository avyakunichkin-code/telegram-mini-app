## 1. Сохранность незавершённого ввода

Факт: Refine сохраняет раздел по действию пользователя, а текущие строки и
отредактированные поля кредита находятся в памяти компонента. Перезагрузка
их теряет. Сетевое отключение уже обработано; повторять его реализацию не нужно.

Первый срез: восстановление в той же вкладке через sessionStorage, только для
актуального draft и той же сессии. Это дополнительная копия анкеты; не помещать
её в CacheStorage или существующий cache итоговых отчётов. Закрытие вкладки не
обещает продолжения. Между устройствами работает только сохранённый сервером ввод.

Снимок: version, SHA-256 fingerprint сессии (без токена), checkup_id,
active_section, исходные серверные строки раздела, текущие строки, edited loan
fields, saved_at. TTL 24 часа — предлагаемый параметр. Хранить только один
редактируемый раздел. Не копировать e-mail, members или полный отчёт.

После загрузки авторизованного draft сравнить исходные строки с серверными:
если сервер изменился, не применять локальные строки автоматически; предложить
сохранённый сервером вариант или локальный ввод. Другой пользователь, сессия,
completed, неверная схема, истёкший TTL → очистить. Logout/401/delete и storage
session change очищают снимок; поздняя запись после logout запрещена epoch guard.
После успешного PUT и GET удалить снимок, затем начинать новый раздел.
При отказе storage ввод остаётся в памяти, видимое предупреждение говорит,
что перезагрузка потеряет несохранённое. Ошибка PUT не очищает снимок.

CS: строка с пустой границей → reload → те же строки и раздел; estimated-кредит
не становится точным; смена пользователя не восстанавливает ввод; конфликт
сервера не затирает данные; storage denied; logout во время записи; успешное
сохранение не воскрешает старый снимок. Desktop и 375 px.

## 2. Влияние уточнения

Существующий бейдж precision остаётся оценкой ввода, не вероятностью прогноза.
Новый блок отвечает на вопрос, меняется ли вывод при допустимых границах.
Первая реализация ограничена чувствительностью месячного свободного потока:
остальные входы фиксированы по действующим правилам, меняется один диапазон.
Не выдавать её за полный прогноз ликвидности или доказанную точность.

API: авторизованный POST /api/checkups/{id}/preview с mode=sensitivity,
section (incomes/expenses), row_index (0–49); поле amount фиксировано.
У доходов/расходов нет стабильного row_id: индекс относится к сохранённому
чекапу, после его изменения клиент сбрасывает preview. Сервер проверяет владение
и allowlist полей. Ответ:
rules_version, as_of, baseline и два endpoint-результата free_cashflow с
допущениями и предупреждениями. Сценарий не сохраняет чекап, шаги или события.
Расчёт через адаптер Plan и fincore; формулы не дублировать в React.
Неподдержанное поле → понятный отказ, без нулевого результата.

Контракт ошибок: 401 без текущей Plan-сессии, 404 чужой/неизвестный checkup_id,
422 неизвестный mode/section/index, лишние поля, отрицательные/нечисловые
суммы и horizon вне 1–12; 409 completed без сохранённой поддержанной версии
rules_version. Старые GET/PUT/complete и отчёты совместимы, схема БД не меняется.
Sensitivity baseline — объект free_cashflow, endpoints — два объекта
input/free_cashflow. Contribution baseline/alternative — помесячные массивы
month/cash/available_after_contribution/cushion/transferred. nullable только
first_shortfall_month (null = хватало для всех запрошенных переводов).
Нулевой monthly_amount допустим, нулевой horizon — нет. Финансовые суммы
входа используют действующий Money (Decimal, до двух знаков), выход — числа.

Кандидат по весу precision не называется наиболее влиятельным без сравнения
всех поддержанных полей. Первый UI говорит «Проверить влияние этого диапазона».
Не называть base/pessimistic независимыми эффектами одного поля.

## 3. «Что, если» без изменения исходных данных

Первая поставка: только дополнительный регулярный взнос в подушку. Перенос цели
и досрочное погашение — последующие срезы, после проверки первой модели.
Это перевод между своими средствами, не потребление и не рост капитала.
Нельзя просто прибавить взнос к прогнозу общего имущества.

Тот же preview endpoint: mode=cushion_contribution, monthly_amount, horizon_months
(1–12). Ответ: baseline/alternative, available_after_contribution, cushion_delta,
first_shortfall_month, assumptions. Проверить доступность денег помесячно;
не обещать перевод при дефиците. Счёт и резерв различаются; недоступный reserve
не считать свободным cash. Без записи в чекап, шагах, истории и событиях.
Отмена возвращает исходный вид. Старые итоговые отчёты не пересчитываются молча:
preview только с поддержанной rules_version; иначе явно недоступен.

CS: нулевой взнос даёт baseline; отрицательный/нечисловой отклоняется;
взнос > остатка показывает нехватку; исходный DTO не мутирует; чужой id → 404;
ошибка/поздний ответ не заменяет актуальный сценарий; офлайн preview недоступен.

## 4. Шаг и ожидаемый результат

Существующие StepActions и PreviousStepBridge сохраняются. Новый текст рядом
с текущим шагом объясняет исходную метрику, допущение и ожидаемое направление.
Фактическая разница берётся только из следующего чекапа. Не писать «вы увеличили
подушку» на основании checkbox. Если шаг завершён вручную, показать этот факт.
Для stop_deficit не предлагать переводить деньги в резерв. Нет подтверждённого
численного расчёта → только качественное ожидание без выдуманной суммы/даты.

## 5. Проверка понятности и измерение

Параллельно: [протокол](../research/PLAN_understanding-session.md), только
синтетические семьи. Это исследование интерфейса, не допуск реальных анкет.
Существующие события P3-09 не расширять суммами или свободным текстом.

P3-10: сначала контракт агрегатов; не подключать admin игры. Когорта чекапов
по серверному created_at в [from,to) UTC. Один checkup = одна единица;
повторные report_viewed и step_done дедуплицируются. Final-view conversion:
чекапы с первым report_viewed(final=true) / старты. Step conversion: чекапы,
где есть step_done в течение 30 суток после первого final view / чекапы с
полным 30-дневным окном наблюдения после final view. Незрелые отдельно.
При отсутствии checkup_id у события не угадывать привязку по последнему чекапу:
показать неприсоединимые события и подготовить отдельный контракт исправления.
Серверные duration_seconds — полное время от создания, не активное время ввода.
Медианы quick_done и checkup_completed отдельно, один milestone на чекап.
Нулевой знаменатель = null, не 0%. Приводить числитель и знаменатель.

Админ endpoint и CSV пока не реализуются: нужна отдельная авторизация Plan,
контракт границ окна и запрета PII; пользовательский JWT недостаточен.
Протокол наблюдения не подменяет этот серверный отчёт и не доказывает конверсию.

## Дизайн и порядок реализации

Два варианта на одинаковом вымышленном кейсе: A «Рядом с решением» и
B «Мастер проверки». [Lab](../../design-lab/plan-checkup/decision-value-round/index.html).
Оба показывают сохранность, чувствительность, сценарий и шаг; состояния
loading/empty/error/offline доступны в lab. Рекомендация — A: сохраняет
утверждённый атлас, добавляя контекст по месту. B — более последовательный путь.

1. Утверждение поведения сохранности и варианта UI → реализация с FE unit/E2E.
2. Отдельный additive API-контракт preview → API/FE совместно, Plan pytest.
3. Шаг с ожиданием, без повторной реализации отметок и истории.
4. Исследование на синтетических кейсах параллельно; P3-10 по контракту.

Готовность: обновлённый canon после approval, unit/build/guardrails, desktop/mobile
E2E; backend pytest при API/логике; shared fincore без изменений. Деплой, реальные
анкеты, рассылка и смена финансовых порогов в этот срез не входят.
