## Продуктовые изменения

Идеи, specs, планы и исследования принадлежат plan/docs. Используй существующий
roadmap и текущий согласованный срез. Plan — календарный финансовый чекап;
игровые ходы, needs, события и victory не входят в его модель.

## API и БД

API: plan/api/plan_api/main.py и schemas.py; сценарии/данные — repo.py, analysis/
и профильные модули. Потребитель — plan/web/src/api.js и screens/. Формат ошибок,
auth и совместимость бери из текущего кода и API-тестов. Новый контракт меняет
сервер и потребителя вместе, включая негатив изоляции пользователей по риску.

Миграции — plan/api/migrations; runner — plan_api.migrate поверх tvoy_platform.
Проверь settings.MIGRATIONS и runner перед выбором команды. На явно выбранном
изолированном стенде команда из plan/api: python -m plan_api.migrate.
Не применять игровой db.sh/baseline/bootstrap к PLAN. Тесты используют SQLite;
если изменено PostgreSQL-поведение, одной SQLite-проверки недостаточно.

P2 разрешён ADR-017; условия реальных пользователей, данных и деплоя остаются
в ADR и roadmap. В текущих проверках только синтетические данные, письма — заглушка.
Тестовый успех не снимает gate публикации или реального входа.

## UI и проверки

UI следует [DESIGN](../DESIGN.md): lab → явное человеческое approval → компоненты
PLAN → состояния и соответствие. MQX-процесс GAME не является процессом PLAN.
Мелкие layout-neutral исправления проверяются локально по затронутому поведению.

Из plan/api: pytest в среде PLAN; из plan/web: test:unit и build, критичный путь —
test:e2e. Общий ui-kit/api-client проверяется отдельно по изменённому контракту.
Обычная задача PLAN не требует GAME suites; изменение fincore или другого общего
контракта требует проверки затронутых потребителей по общему маршруту.
