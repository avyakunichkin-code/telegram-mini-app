# Reference: DB Baselines and Migrations

## Когда добавлять индекс

- **PK/UNIQUE**: уже индексируются (не дублировать).
- **FK колонки**: индексировать только при реальном чтении по ним (join/filter).
- **Комбинированные индексы**: делать под конкретные `WHERE (a = ? AND b = ?)` или `ORDER BY`.

## Как писать data-migration безопасно

- Делай DML **идемпотентным**:
  - `UPDATE ... WHERE ... AND field <> target_value`
  - `INSERT ... ON CONFLICT ... DO NOTHING/UPDATE`
- Всегда оцени «сколько строк затронем»:
  - добавляй узкие `WHERE`‑условия
  - если апдейт массовый — разбивай на пачки или делай offline (если потребуется)

## Baseline: рекомендуемая структура файла

1. Заголовок (что это, как регенерировать)
2. `CREATE TABLE ...` (итоговая схема, без истории миграций)
3. `CREATE INDEX ...` (только нужные)

## Полезные статические проверки

- DML в baseline:
  - искать `INSERT|UPDATE|DELETE`
- Дубли индексов:
  - одинаковые колонки/условия
  - индексы на `id` при PK

## “Если нужно удалить/переименовать колонку”

Используй паттерн **expand/contract** (безопасная эволюция схемы):

1. **Expand**: добавить новое поле/таблицу (сначала nullable/совместимо по дефолтам).
2. **Dual-write**: временно писать в старое и новое (если нужно) на уровне приложения.
3. **Backfill**: data-migration с узким `WHERE`, идемпотентно.
4. **Switch reads**: переключить чтение на новое поле (фича-флагом или явным релизом).
5. **Contract**: удалить старое поле отдельной миграцией после периода стабильности.

Правило: **никогда не делай rename/drop как “один шаг”**, если есть хотя бы минимальный шанс отката/частичного деплоя.
